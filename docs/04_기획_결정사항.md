# 04. 기획 결정 사항

참고 문서 두 개(신청서 초안 `케어모드반영`, 아이디어 검토·개발계획 PDF)는 몇 군데 방향이 다릅니다. 코드를 어떻게 맞췄는지와, 팀이 정해야 할 것을 적어 둡니다.

## 코드에 반영한 방식

| 주제 | 신청서 초안 | 검토 문서 | 현재 코드 |
|---|---|---|---|
| 케어 모드 | MVP 에 포함 | 핵심 범위에서 제외 권고 | **포함** (최신 신청서 기준). 판단 로직은 core 에 분리하고, 시연은 '빠른 판단' 으로 재현 |
| 선택 없이 출발 | 직전 운전자로 자동 지정 | 미선택 기록이 직전 운전자에게 붙으면 안 됨 | 직전 운전자로 지정하되 **'미확인'** 으로 따로 기록·표시 (두 요구를 함께 충족) |
| 앱 실행 | 시동·문 열림 시 자동으로 뜸 | P0 는 수동 실행 | **수동 실행.** 실행 중일 때만 문 개폐로 재확인. 자동 실행은 설명회 확인 후 |
| 교대 감지 | P + 운전석 문 개폐 → 자동 재확인 | 짐 꺼내기 등 오탐 가능 | 재확인 화면에 **'그대로 운전해요'** 버튼, 응답 없이 출발하면 같은 운전자 유지 |
| 메모 | 읽으면 끝 | 읽음과 해결 분리 | **읽음 ≠ 해결.** 해결 전까지 모두에게, 작성자에게도 보임 |
| 경고등 | 메모와 함께 브리핑 | 메모 해결이 경고를 가리면 안 됨 | 경고등은 차량 값으로만 표시, 메모 처리와 독립 |
| 변화 비교 | 지난 운전 이후 새 경고등 | 내 마지막 확인 대비 변화 + 관측 시각 | **운전자별 마지막 확인** 시점과 비교, 모든 값에 시각 표시 |
| 통행료 | Toll SDK 로 자동 기록 | 공개 API 에 결제 금액 없음 | **제외** |
| 유류비 분담 | 연료 사용량으로 자동 정산 | 연료 % 는 실제 비용과 다름 | 운전자별 **거리·시간 기록까지만** |
| 운전자 추천 | "가장 안전한 운전자" | 판정 표현 지양 | "컨디션 참고" + "추천해요" 수준. 근거는 **3단계(좋음/보통/휴식 필요)만** 표시 |
| 건강 데이터 공유 | 차량·다른 파티원에게는 3단계만 | — | 차량 화면(추천 문구·설정)에 수면 시간 등 원래 수치를 보여 주지 않음. 원래 수치는 본인 폰에서만 |
| 차량 데이터 지연 | "지연 없음" | 수신·연결·지원 여부가 따로 있음 | 받은 시각·오래된 값·미지원을 화면에 표시 |

## 공유 차량 관점에서 더한 것 (2026-10-28)

여러 사람이 회사 차 3대를 번갈아 쓰는 현장 사례를 참고했습니다. 험하게 운전하거나 사고가 나도 처리 없이 다음 사람에게 넘어가고, 회사도 따로 확인하기 어려웠습니다. 가족 차에서도 같은 일이 작게 일어나므로, 인수인계 흐름 안에 넣었습니다.

| 주제 | 결정 | 이유 |
|---|---|---|
| 사고 후 그냥 넘김 | 운행 중 급정거가 있었으면 주차 직후 **"차에 이상이 있나요?"** (없어요 / 있어요 → 신고) | 기억이 생생할 때, 한 번 누르면 끝나게 |
| 넘겨받은 차 확인 | 브리핑 아래 버튼 두 개로 **인수 점검**: 확인했어요 / 이상이 있어요. 결과는 `Inspection` 으로 저장 | 발견 시점을 남겨야 "언제부터"를 좁힐 수 있음 |
| 책임 소재 | **원인을 단정하지 않음.** 인수 점검에서 발견하면 직전 운전자와 주차 시각만 함께 기록하고 "확인이 필요해요"로 표시 | 가족·동료 사이 갈등 방지, 오탐 가능성 |
| 처리 추적 | 처리 필요 → 처리 중(수리·보험 맡김) → 처리 완료(다 고쳤어요). **완료 전까지 모든 운전자 브리핑 맨 위** | 메모처럼 "읽으면 끝"이 되지 않게 |
| 신고 입력 | 키보드 없이 종류 5개 + 차 그림에서 위치 5곳 | 차량 화면에서 입력 부담 최소화 |
| 운전 습관 | 급정거·급가속 **횟수만** 기록. 점수·순위·"난폭 운전" 표현 없음 | 감시 앱이 되지 않게 |
| 급정거 기준 | 3.5m/s² 이상 감속, 급가속 3.0m/s² 이상, 같은 종류는 3초 안에 한 번만 셈 | 일반 제동(약 2.5m/s²)과 구분. 속도 신호만으로 계산 |
| 면허 정보 | 종류·갱신일·취득 연도만. **면허 번호는 받지 않음** | 면허 번호는 개인정보 보호법상 고유식별정보라 별도 근거·동의가 필요. 기능에 필요하지 않음 |
| 면허 갱신 | 60일 전부터 "면허 갱신 N일 남음", 지나면 경고 색 | 고령 운전자는 적성검사 주기가 짧음(케어 모드와 연결) |
| 초보 운전 | 취득 2년 미만이면 "초보 운전" 배지 | 도로교통법상 초보운전자 기준(연도로 근사) |
| 사업 확장 | 같은 구조를 소규모 법인 차량(여러 직원이 몇 대를 공유)에 쓸 수 있음. 관리자용 화면은 폰·웹 확장으로 | 참가신청서의 B2B 모델과 연결 |

## 쉬운 화면으로 정리 (2026-10-29)

엄마·아빠·할아버지(40~70대)가 처음 봐도 쓸 수 있게 화면을 줄였습니다.

| 화면 | 바꾼 것 | 옮기거나 뺀 것 |
|---|---|---|
| 공통 | 큰 버튼은 화면마다 2개까지, 나머지는 글자 버튼. 배지 대신 한 줄 문장 | 출처 라벨("차량에서 감지"), 갱신 시각, 누적 km |
| 운전자 선택 | 이름을 크게, 알릴 것은 두 개까지(오늘 추천 · 면허 갱신 N일 남음 · 초보 운전 · 지난번 운전) | 카드마다 붙던 컨디션 배지 → 위쪽 추천 한 줄로 |
| 브리핑 | 왼쪽 차 그림 + 숫자 두 개, 오른쪽 달라진 점 문장 목록. 버튼: 확인했어요 / 이상이 있어요 | 메모 카드의 읽은 사람 목록, '다시 듣기'는 머리말 글자 버튼으로 |
| 홈 | 차 상태 + "알려 드릴 것"(사고·파손, 남은 메모). 버튼: 메모 남기기 / 운전 끝내기 | 최근 운행 → 기록 화면 |
| 메모 | 이 차에 맞는 버튼만(주유 또는 충전), 사고·파손 신고를 같은 격자에 | 아래 버튼 3개 → 2개 |
| 사고·파손 신고 | ① 무슨 일 ② 어디(모르면 건너뛰기) 두 단계 | "지금 상태" 고르기 → 나중에 알림에서 |
| 설정 | 가족 프로필 2×2, 문제 있을 때만 배지 | "면허 유효" 같은 정상 배지 |

브리핑 문장도 소리 내어 읽기 좋게 고쳤습니다. 예: "연료: 마지막 확인 때 45% → 지금 12%" → "연료가 지난번 45%에서 지금 12%로 줄었어요".

## Pleos SDK 확인 결과에 따른 결정 (2026-10-29)

| 확인한 사실 | 결정 |
|---|---|
| 계기판 경고등(telltale)·타이어 공기압 값은 `PRIVATE_CAR_SAFETY` 필요 | 서드파티 앱은 못 받으므로 쓰지 않음. 브리핑에 "경고등 정보: 이 앱에서는 볼 수 없어요"를 작은 글씨로 알리고, 특이사항이 없을 때도 "새 경고등 없음"이라고 말하지 않음. 발표에서 "경고등 연동"을 주장하지 않음 |
| 엔진오일·브레이크액 레벨, 워셔액 부족은 `CAR_SAFETY` 로 가능 | 이 셋을 소모품 경고로 받음 |
| Pleos 에뮬레이터 차량은 전기차 | 배터리 %를 우선 쓰고, 메모 버튼도 '충전 필요'만 보이게 함 |
| P로 바꾼 뒤 주행 제한이 조금 늦게 풀림 | 그 사이 띄운 '주차 후 메모'를 잃지 않게 처리 |
| 속도는 초당 5번(0.2초 간격) 들어옴 | 0.5초 이상 떨어진 두 값으로 가속도 계산. 가속 페달을 6초 끝까지 밟으면 두 번 세던 것을 '기준의 절반 아래로 내려가야 다시 셈'으로 고쳐 한 번만 셈 |
| 누적 주행거리는 값이 그대로여도 몇 초마다 다시 옴 | 화면 갱신은 값이 실제로 바뀔 때만 |

## 휴게소 안내 연동에서 정한 것 (2026-10-29)

| 확인한 사실 | 결정 |
|---|---|
| NaviHelper 는 경로·경유지 설정은 되지만 주변 검색이 없음 | 전국 휴게소·졸음쉼터 1,004곳(OpenStreetMap, ODbL)을 앱에 넣고, 진행 방향 앞쪽 ±60° 안에서 가장 가까운 곳을 골라 내비에 넘김. 앞쪽에 없으면 가장 가까운 곳 |
| 고속도로 휴게소는 방향마다 따로 있음 | 진행 방향(heading)으로 거름. 같은 거리의 반대 방향 휴게소를 구별하는 데는 한계가 있어 '방향' 이름은 쓰지 않음 |
| 목적지가 있으면 경유지, 없으면 경로 요청 | 목적지가 있으면 첫 번째 경유지로 추가, 없으면 쉼터까지 바로 안내 |
| 경로 계산이 5초 넘게 걸리기도 함 | 10초까지 기다리고, 늦으면 "요청은 보냄"으로 처리. 안내가 시작되면 내비가 알려 준 도로 거리·시간을 씀 |
| 에뮬레이터의 FusedLocation 은 안드로이드 기본 GPS(미국)를 돌려줌 | 경유지는 내비 경로에 더하는 것이라 내비의 현재 위치를 먼저 쓰고, 없으면 FusedLocation |
| 보호자 알림의 위치 | 내비가 알려 주는 주소("수정구 시흥동")를 그대로 씀. 위치는 케어 모드 3단계에서만 읽고 저장하지 않음 |
| adb 설치 앱은 주행 중 허용 목록(DO)에 없음 | 에뮬레이터 시연에서 기어 D 로 앱을 새로 띄우지 않음. 정식 배포 때 App Market 심사로 DO 허용을 받음 |

## 말로 남기는 메모 · 큰 글씨에서 정한 것 (2026-10-29)

| 확인한 사실 | 결정 |
|---|---|
| SpeechToText 는 HYBRID·SERVER 모드에 Pleos Playground 앱 등록(Client ID/Secret)이 필요 | **ON_DEVICE**(차량 내장 엔진)만 씀. 네트워크·등록 없이 동작하고, 말한 내용이 차 밖으로 나가지 않음 |
| 인식 결과가 틀릴 수 있음(합성 음성 "주유" → "주의") | 바로 저장하지 않고 **"이렇게 남길게요"** 확인. 주차 중: 남기기 / 다시 말하기. 주행 중: 화면을 안 눌러도 되게 읽어 준 뒤 **5초 뒤 자동 저장**, 취소 가능 |
| "~하라고 전해 줘" 같은 옮기는 말투는 메모로 어색함 | 부탁하는 말과 받는 사람을 떼고 "~해 주세요" / "~해요"로 바꿈. 규칙에 없는 말은 **뜻을 바꾸지 않도록 그대로** 둠 |
| "엄마한테 …"처럼 받는 사람을 말함 | 받는 사람을 표시하지만 차 문제는 모두 알아야 하므로 **모든 운전자에게 보임** |
| 주행 중 안부 확인과 겹칠 수 있음 | 케어 모드 "괜찮으세요?"가 뜨면 말로 남기기를 닫음(안전이 먼저) |
| 글씨만 키우면 버튼 밖으로 넘침 | 큰 글씨 모드는 **화면 전체를 1.2배**(글씨·버튼·간격 같은 비율). 해당 운전자가 운전할 때만 |
| 큰 글씨에서 메모 화면 마지막 줄이 잘림 | "말로 남기기"를 머리말 버튼으로 옮겨 모든 칸이 한 화면에 보이게 함 |
| 마이크 없는 가상 빌드 | 예시 문장을 골라 "말한 것처럼" 처리(실제 차에서 할 말을 함께 보여 줌) |

## 회사 차 모드에서 정한 것 (2026-11-03)

심사 기준의 사업성(수익 모델의 핵심이 법인·사업장 구독)을 목업 그림이 아니라 실제 차량 앱으로 보여 주려고 넣었습니다.

| 확인한 사실 | 결정 |
|---|---|
| 법인 업무용승용차는 연간 관련비용이 1,500만원을 넘으면 **운행기록부**로 업무사용비율을 입증해야 비용으로 인정됨(법인세법 시행령 제50조의2, 국세청 고시 서식). 손으로 적는 곳이 많음 | 회사 차 모드의 핵심을 **운행기록부 자동 작성**으로. 서식 칸 중 차가 아는 것(주행 전·후 계기판 누적거리)은 Vehicle SDK 에서, 사람 정보(부서·성명)는 운전자 선택에서, 업무 여부는 버튼 한 번으로 |
| 서식의 업무용 사용거리 = 출퇴근용 + 일반 업무용 | 목적 버튼은 **출퇴근 · 일반 업무 · 개인 용무** 셋. 업무사용비율 = (출퇴근 + 일반 업무) ÷ 총 주행거리 |
| 목적을 안 고르고 출발할 수 있음 | 막지 않고 '목적 미입력'으로 표시, **업무용으로 치지 않음**(보수적으로). 주차 중 홈에서 '목적 바꾸기' |
| 같은 사람이 문을 열고 닫았다가 이어서 타면 | 목적을 그대로 이어 감 |
| 직원의 수면·심박으로 운전자를 추천하거나 케어 모드로 살피면 감시로 받아들여질 수 있음 | 회사 차에서는 **컨디션 추천·케어 모드를 끔**. 설정에 이유를 적어 둠 |
| 사고·파손은 회사에서는 관리자가 처리 | 신고 문구를 "관리자에게 보고했어요"로. 처리 상태 변경은 차에서도 가능(관리자 화면은 서버 확장) |

## 팀이 정해야 할 것
1. **케어 모드를 발표의 중심에 둘지, 확장 기능으로 소개할지.**
   검토 문서는 인수인계 하나에 집중하라고 권합니다. 코드는 둘 다 가능하게 되어 있으니, 발표 구성만 정하면 됩니다.
2. **신청서 문구 수정 여부.** 검토 문서가 수정을 권한 표현:
   "전달 수단이 없다", "가장 안전한 운전자를 추천", "차량 데이터라 지연 없음", "문이 열리면 자동 실행", "Toll SDK 로 통행료 자동 기록", "사용자가 자동으로 계속 앱을 연다"
3. **팀 구성·역할** (신청서 A·B 항목). 검토 문서의 가정: 차량 앱 / 앱 기능·데이터 / 기획·검증 3명.
4. **GitHub 저장소 공개 여부와 저장소 이름.** 실명·개인 이메일이 커밋에 남지 않게 설정 ([01 문서 9번](01_개발환경_세팅.md#9-github에-올리기-전-확인)).
5. **공유 차량(법인) 확장을 발표에 넣을지.** 가족 시나리오가 중심이고, 사고·파손 처리는 "가족에서도 생기는 문제"로 소개하는 안을 권합니다. 쓸 경우 [법인차 관리 목업](pt/README.md)과 차량 앱의 **회사 차 모드(운행기록부 자동 작성, 11/03)**가 있습니다.
6. **팀명.** 제출 APK 이름이 `팀명_CarRelay_release.apk` 형식이라 정해지면 `apk/CarRelay_release.apk` 이름만 바꾸면 됩니다(영어 권장).
7. **어느 APK 를 제출할지.** Pleos SDK 빌드(`CarRelay_release.apk`)를 권합니다. 심사 환경에 Virtual Console 이 없으면 가상 차량 빌드가 시연하기 쉽습니다. 둘 다 `apk/` 에 있습니다.
